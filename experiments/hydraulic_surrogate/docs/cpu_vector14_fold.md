The proposed6GiB fit budget has a source-based rationale. The [3.4.1 histogram implementation](https://raw.githubusercontent.com/dmlc/xgboost/v3.4.1/src/tree/hist/histogram.h) maintains builders per target, and the [histogram cache](https://raw.githubusercontent.com/dmlc/xgboost/v3.4.1/src/tree/hist/hist_cache.h) stores precise gradient pairs per bin/node. A depth6 tree's63 internal-node histogram set at664×128 bins and14 targets is about1.12GiB before scratch and other allocations. This component depends on bins, targets and nodes rather than training rows. [Thread scratch](https://raw.githubusercontent.com/dmlc/xgboost/v3.4.1/src/common/hist_util.h) depends on which nodes each thread processes; the extra32-node/two-thread upper calculation is about0.57GiB and actual allocation can be smaller.

At146899 rows, float32 features are390.2MB and14 gradient/Hessian pairs about16.5MB. The [gradient index](https://raw.githubusercontent.com/dmlc/xgboost/v3.4.1/src/data/gradient_index.h) uses compressed indices for dense data; one-byte indices would add97.5MB, with sketch/copy/metadata buffers additional. Installed3.4.1 `sklearn.py` selects QuantileDMatrix for histogram fits. Thus multiplying the entire2.57GiB pilot peak by14.7 is unjustified. Doubling bins to256 would roughly double the histogram term; it is a calculation only, and the protocol keeps128. Official-version source snapshots and exact arithmetic are in `artifacts/cpu-vector14-memory-review-001`.

The build and fit use separate processes so the full664 DataFrame is released before training.
