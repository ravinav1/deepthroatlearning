# Optional four-worker continuation

The current two-worker run remains unchanged. At 19:02 UTC it had 387 complete cases and zero failures. Across 726 finished attempts, the largest worker RSS was 0.879 GB (95th percentile 0.659 GB); two extra workers would add at most 1.758 GB if the observed maximum holds. The machine reports 32 GiB physical memory, 54% system-wide free, 8.72 GB inactive pages and no swap activity. These measurements support testing a 3 GiB additional allocation before a four-worker continuation. They do not establish an upper bound for unseen harder MILP cases. The sandbox denies process RSS queries; persisted per-worker resource proofs supply the observed measurements.

The existing source cannot drain on request: it has no signal handler or stop-file hook, and its queue remains fixed. Changing the file would not safely change the already running process and would violate the frozen source contract. A second job on disjoint future cases would eventually duplicate the original queue. Therefore a clean change requires a separately audited continuation runner and a recorded interruption of the old coordinator after approval. No interruption has been sent.

Proposed continuation implementation:

1. Preserve the original protocol, builder, every completed case directory, and all original attempt records unchanged. Copy the orchestration into a new separately named four-worker runner. Its mathematical functions import the exact original frozen solver, matrix builder, proof verifier and feature module. Only execution orchestration, compatible reuse, and graceful draining are new.
2. Freeze a new execution protocol. An explicit compatibility comparison must require equality of every original protocol field except version, creation time, worker count, execution source listing and the resume-policy text. All physical sources, solver version/threads, inputs, metadata, control arrays, 60/600-second status-only retry rule, both fresh MILP and fixed LP replay requirements, canonical diagnostics, pilot evidence, feature formulas and 664-column prefix remain exact. Preserve both protocols and hashes in the new aggregate proof.
3. After source review, allocate and touch 3 GiB in a short separate process, inspect memory pressure and swap counters while held, then release it. Abort the switch if pressure becomes unhealthy or swap grows. This probe has not been run. It is a resource check, not a solver or model experiment.
4. The original coordinator can only finalize through an interruption. Its ProcessPoolExecutor context waits for active tasks before the outer failure handler writes a finalized manifest. Thus a normal SIGINT to the coordinator is expected to preserve immutable completed cases, but the two active task results may remain unindexed. Record the original run as an interrupted execution, not a failed modeling hypothesis. Wait for the finalized original manifest and workers before proceeding. Do not force-kill workers. Prove this drain behavior on a synthetic small-process harness before issuing any live signal.
5. Import only fully verified complete cases from the explicitly hashed finalized original manifest. Copy their raw arrays, feature arrays and original complete.json byte for byte, preserving the latter as original_complete.json. Publish a separate new compatible-import receipt referencing the old proof and new execution protocol; never rewrite the old proof in place. No partially completed case is silently promoted. At most the active incomplete case is recomputed from scratch, with original partial evidence retained in the old run.
6. New cases use four workers with one solver thread each, fresh processes, identical attempt limits and replay gates. A new stop-file or SIGINT handler stops queueing, lets all active results publish and records a resumable incomplete manifest. Resource guards check before scheduling further work. All exceptions, retries and failures remain visible; there is no LP substitution.
7. Before a later feature loader or model package can use the aggregate, an independent audit must verify both lineage branches and their exact feature/input compatibility. The compact loader can retain its existing all3647-complete requirement; the new protocol and manifest must explicitly enumerate compatible imported proofs. No learned-model promotion is authorized by this execution change.

Expected gain is approximately twofold throughput only if CPU and memory bandwidth permit. Fresh-process startup, proof publication, serial input verification, tail cases and contention may reduce that. With roughly 3260 cases remaining, measured per-attempt CPU wall time suggests several hours at two workers versus roughly half that at four; the saved time must exceed the preparation/drain overhead. It is reasonable to continue the current job while the new runner is reviewed.

Measurements and unchanged-run evidence are saved in `artifacts/integer-water-budget-four-worker-feasibility-001/manifest.json`.
